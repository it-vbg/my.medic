# my.medic

my.medic — семейный веб-кабинет для медицинских документов. В нём можно вести свою карту и карту ребёнка, предоставить супругу доступ к конкретной карте и сохранить оригиналы анализов и обследований. Подготовка к приёмам и общая книга рецептов входят в план развития.

## Запуск с PostgreSQL

Кабинету нужны Node.js 24 или новее, PostgreSQL 16 или новее и SMTP для подтверждения почты. Next.js подключается к базе напрямую. Оригиналы PDF, JPEG и PNG до 12 МБ записываются вместе с описанием в поле `bytea`. В браузере файл открывается через кабинет, который проверяет права при каждом запросе.

Создайте отдельную базу и роль приложения. В Linux с установленным PostgreSQL для этого подойдут следующие команды.

```sh
sudo -u postgres createuser --pwprompt medic_app
sudo -u postgres createdb --owner=medic_app medic
```

Скопируйте [.env.example](.env.example) в `.env.local` и заполните четыре переменные.

| Переменная | Значение |
| --- | --- |
| `DATABASE_URL` | Строка подключения, например `postgresql://medic_app:PASSWORD@127.0.0.1:5432/medic`. Специальные символы пароля в URL кодируются. |
| `APP_URL` | Адрес кабинета для ссылок из писем. Локально подойдёт `http://127.0.0.1:3000`, на VDS укажите публичный HTTPS-адрес. |
| `SMTP_URL` | Для локальных проверок подходит SMTP-порт Mailpit. Для отправки на обычные адреса укажите SMTP-сервер своего почтового провайдера с TLS. |
| `SMTP_FROM` | Имя и адрес отправителя, например `my.medic <cabinet@example.org>`. На VDS используйте подтверждённый адрес своего домена. |

В корне проекта выполните следующие команды. Миграция создаёт схему `medic`. Повторный запуск проверяет уже применённые файлы.

```sh
npm ci
npm run db:migrate
npm run dev
```

Откройте [кабинет в браузере](http://127.0.0.1:3000), зарегистрируйтесь и перейдите по ссылке из письма. Введите выбранный пароль, чтобы подтвердить адрес и открыть личную карту. При тестировании с Mailpit письма видны в его локальном веб-интерфейсе.

## Размещение на VDS

Выделите приложению системного пользователя. Закройте его `.env.local` правами `chmod 600 .env.local`. Для базы на том же сервере используйте интерфейс loopback. После установки зависимостей и применения миграции соберите кабинет и запустите из каталога проекта.

```sh
npm run build
npm start -- --hostname 127.0.0.1 --port 3000
```

Для постоянной работы задайте команду запуска и рабочий каталог в systemd или в панели VDS. Направьте HTTPS-трафик домена на `127.0.0.1:3000` через обратный прокси. Он должен сохранять исходный `Host` и передавать `X-Forwarded-Proto: https`. Если используете nginx, задайте `client_max_body_size 13m`, чтобы принимались файлы размером 12 МБ вместе с полями формы. [Размещение Next.js на своём сервере](https://nextjs.org/docs/app/guides/self-hosting)

Кабинет ограничивает попытки регистрации, подтверждения почты и входа до вычисления хеша пароля. За 15 минут допускается до 10 попыток входа и до 5 регистраций на один адрес. Для подтверждения одной ссылки действует лимит в 5 попыток за 15 минут. Общий предел — 120 запросов в минуту на кабинет и 30 за 5 минут на источник.

По умолчанию запросы учитываются как один источник. Для отдельного учёта по IP настройте прокси так, чтобы он перезаписывал `X-Real-IP` адресом клиента (в nginx — `proxy_set_header X-Real-IP $remote_addr;`). Когда порт Next.js доступен только этому прокси, установите `MY_MEDIC_TRUST_PROXY=1`.

### Резервная копия

В архив PostgreSQL попадут аккаунты, права, метаданные и оригиналы документов. Эти команды создают архив и проверяют восстановление в **отдельную пустую базу** на том же сервере.

```sh
set -eu
umask 077
backup_dir=$(mktemp -d "$HOME/medic-backup.XXXXXXXX")
pg_dump -h 127.0.0.1 -U medic_app -d medic -Fc -f "$backup_dir/medic.partial"
mv "$backup_dir/medic.partial" "$backup_dir/medic.dump"
restore_db="medic_restore_$(date -u +%Y%m%d%H%M%S)"
sudo -u postgres createdb --owner=medic_app "$restore_db"
pg_restore -h 127.0.0.1 -U medic_app -d "$restore_db" --no-owner --single-transaction "$backup_dir/medic.dump"
```

Для рабочего сервера храните зашифрованную копию вне VDS и периодически проверяйте восстановление. При возврате рабочего кабинета к старому архиву сначала завершите восстановленные сеансы, аннулируйте ожидающие подтверждения и приглашения. Перед открытием кабинета учтите отзывы семейного доступа, сделанные после даты архива. [Резервное копирование PostgreSQL](https://www.postgresql.org/docs/current/backup-dump.html)

## Доступ к прежней локальной базе SQLite

Чтобы открыть прежние данные на компьютере владельца, укажите `MY_MEDIC_STORAGE=sqlite` и запустите `npm run dev`. Кабинет откроется на `127.0.0.1:3000`. В этом локальном режиме регистрация завершается сразу после ввода почты и пароля. Файл по умолчанию находится в `.my-medic/cabinet.sqlite`. Для другого каталога задайте `MY_MEDIC_DATA_DIR`. У SQLite и PostgreSQL отдельные аккаунты и документы.

## Первая загрузка и доступ семьи

1. После подтверждения почты откроется личная карта. В разделе семейного доступа можно создать отдельную карту ребёнка.
2. Выберите карту, нажмите «Загрузить документ», укажите категорию и дату исследования. Поддерживаются PDF, JPEG и PNG размером до 12 МБ. Сохранённый оригинал можно открыть из списка.
3. Чтобы супруг увидел вашу карту или карту ребёнка, откройте управление доступом именно для этой карты. Укажите почту его аккаунта и передайте ему выданный код лично. Супруг входит в свой аккаунт и принимает приглашение по коду. Код действует семь дней и используется один раз.
4. Владелец карты может отозвать доступ. Следующие запросы к списку документов и оригиналу проверяют действующие права.

## Разработка

Задачи команды ведутся в [GitHub Issues](https://github.com/it-vbg/my.medic/issues). Основные команды проверки — `npm test`, `npm run typecheck` и `npm run build`. После сборки `npm run test:postgres` проверяет регистрацию по почте, семейный доступ и отзыв прав на настоящем сервере PostgreSQL. Для этого задайте `TEST_DATABASE_URL` с адресом локальной служебной базы `postgres` и отдельной ролью с правом `CREATEDB`. Проверка создаёт временную базу и принимает письма в собственном тестовом SMTP-сервере. `npm run test:e2e` проверяет предыдущий локальный режим SQLite. На Windows используется Microsoft Edge, на других платформах установите Chromium командой `npx playwright install chromium`.

## Порядок разработки

1. **Первый рабочий сценарий в браузере.** В веб-кабинете на Next.js взрослый входит в аккаунт, выбирает свою карту, карту ребёнка или открытую ему карту супруга и загружает PDF или фотографию документа. Создатель карты управляет доступом к ней.
2. **Развитие веб-версии.** В кабинете появятся сверка распознанных результатов с оригиналом, сравнение анализов по датам, ответы ИИ со ссылками на документы, записи к врачу и общий рецепт недели. Сервер будет проверять права пользователя на выбранную карту.
3. **Мобильное приложение на заключительном этапе.** Когда веб-сценарии будут реализованы, начнётся разработка приложения для iOS и Android на React Native и Expo. Через тот же API пользователь получит доступ к своим картам, приёмам и рецептам. На этом этапе добавим съёмку документов из приложения и мобильные уведомления о визитах, контрольных обследованиях и рецепте недели.

## Медицинская карта

- **Документы.** В выбранную карту можно загрузить PDF или фотографию и открыть оригинал. На следующем этапе извлечённые показатели будут связаны со страницей оригинала, чтобы можно было сверить и исправить распознанное значение.
- **Динамика.** Для одного показателя будут видны результаты по датам, единицы измерения и референсные диапазоны с каждого бланка. Для сравнения приложение будет учитывать лабораторию и метод исследования, если он указан.
- **Подготовка к приёму.** ИИ поможет найти рекомендации врача в документах и проверить, есть ли в карте результаты назначенного контроля. Если помощник предложит обсудить дополнительный анализ или консультацию специалиста, он укажет основание и источник. Перед визитом можно будет собрать краткую сводку, вопросы врачу и нужные документы.
- **Приёмы и напоминания.** В веб-кабинете будут видны даты визитов и контрольных обследований. Когда появится мобильное приложение, в нём можно будет включить уведомления и переходить из них к соответствующей записи.

## Семейный доступ

У каждого взрослого свой аккаунт и личная медицинская карта. При загрузке документа родитель выбирает, с чьей картой работает.

| Что доступно | Кто управляет |
| --- | --- |
| Медицинская карта взрослого | Владелец ведёт свою карту и может пригласить супруга к просмотру и загрузке медицинских документов. Приглашение в семейную кухню относится к общим рецептам. |
| Медицинская карта ребёнка | Родитель, создавший карту, выдаёт и отзывает доступ. Приглашённый второй родитель тоже может открывать и добавлять документы ребёнка. |
| Общие рецепты (следующий этап) | Оба взрослых смогут добавлять и редактировать блюда, менять число порций и заменять рецепт недели. |

## Один рецепт на семью

Раз в неделю семья будет получать один рецепт для тех, кто ест вместе. Можно выбрать обоих взрослых и при желании включить ребёнка. У каждого участника свои отметки «люблю», «не люблю» и «не ем». Каждый взрослый также сможет по желанию указать свою диету, например «стол № 5» или Low FODMAP. За ребёнка эту настройку заполняет родитель, который ведёт его карту.

Общий рецепт должен подходить всем, кто будет за столом. Сначала приложение проверит правила выбранных диет и исключит блюда с указанными аллергенами или продуктами с отметкой «не ем». В зависимости от диеты оно учтёт способ приготовления, текущий этап и количество ингредиента в одной порции. Затем среди подходящих блюд выберет то, которое лучше всего учитывает вкусы семьи. Если в книге рецептов нет подходящего блюда, приложение так и сообщит.

Например, если оба любят овощи, а острое нравится одному, приложение сможет предложить запечённые овощи и подходящий по составу соус для отдельной подачи. Оба увидят одну карточку с ингредиентами, порциями и шагами приготовления.
